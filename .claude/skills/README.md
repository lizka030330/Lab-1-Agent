# Навички (Skills) і hooks

Ця тека навмисно порожня. **Навичку ти пишеш сам на третьому занятті** — готового
прикладу тут немає і не буде, інакше вправа перетворюється на копіювання.

Нижче — те, що треба знати до того, як писати: як влаштована навичка, куди її
класти і як увімкнути приклади hooks із `.claude/settings.example.json`.

## Що таке навичка

Навичка — це тека з файлом `SKILL.md`, яку агент підвантажує **за потреби**.
Це не системний промпт і не частина `AGENTS.md`: `AGENTS.md` читається завжди,
а навичка — лише тоді, коли завдання схоже на те, що описано в її `description`.

Навичка потрібна там, де є **повторювана процедура**: «як у цьому проєкті додати
міграцію», «як оформити реліз», «як розібрати лог помилки». Якщо процедура
одноразова — їй місце в промпті, а не в навичці.

## Де вона лежить

```
.claude/skills/<name>/SKILL.md   <- читає Claude Code
.agents/skills/<name>/SKILL.md   <- сюди дивляться інші інструменти
```

Два інструменти — два місця, але правда має бути одна. Тому в репозиторії є
`npm run sync-skills`: скрипт розкладає навички з `.claude/skills/` у
`.agents/skills/`, щоб не редагувати дві копії й не ловити потім розбіжності.
Правиш **тільки** `.claude/skills/`, синхронізацію запускаєш перед комітом.

## Frontmatter: обов'язкових полів рівно два

```markdown
---
name: release-checklist
description: Перевірки перед релізом. Використовувати, коли просять зібрати реліз або тег.
---

Тіло навички: кроки, команди, приклади.
```

- **Обов'язкові:** `name`, `description`. Більше нічого специфікація не вимагає.
- **Опційні:** `license`, `compatibility`, `metadata`, `allowed-tools`.

`description` — це не окраса, а маршрутизація: саме за ним модель вирішує,
відкривати навичку чи ні. Пиши в ньому, **що** робить навичка і **коли** її
застосовувати. Опис на кшталт «утиліти для проєкту» не спрацює ніколи.

## Прогресивне розкриття: чому важливий розмір

Навички побудовані на трьох рівнях завантаження:

1. **Метадані** (`name` + `description`) — приблизно **100 токенів**, вони в
   контексті **завжди**, для кожної навички.
2. **Тіло `SKILL.md`** — вантажиться, коли навичку обрано. Рекомендований
   орієнтир: **до 5000 токенів і до 500 рядків**.
3. **Файли поруч** (скрипти, шаблони, довідники) — модель читає їх сама, коли
   вони справді потрібні. Сюди винось усе довге.

Звідси практичний висновок: десять навичок з роздутими описами з'їдають контекст
у кожному запиті, ще до того, як ти щось спитав. Тримай описи короткими, а тіло —
у межах орієнтира.

## Приклади hooks: `.claude/settings.example.json`

Файл `.claude/settings.example.json` — це **приклад**, він не діє. Робочий
`.claude/settings.json` ти пишеш сам: це вправа першого тижня. Щоб почати,
скопіюй приклад і виправ його під свої правила:

```bash
cp .claude/settings.example.json .claude/settings.json
```

JSON не має коментарів, тому пояснення до обох прикладів — тут.

### Що потрібно, щоб це запрацювало

Обидві команди написані для **POSIX-шелла** і використовують **`jq`**
(так це показано в офіційній документації). На Windows це означає Git Bash і
встановлений `jq` — без нього hook мовчки не зробить нічого: помилка піде в
stderr, а робота агента продовжиться. Перевір, що `jq --version` відповідає,
**перш ніж** робити висновки про те, працюють hooks чи ні.

### Hook 1 — `PostToolUse`, журнал дій

```
mkdir -p .agent-log && jq -c '{ts:(now|todate), tool:.tool_name, input:.tool_input, result:"ok", session:.session_id, source:"claude-code"}' >> .agent-log/session.jsonl
```

Matcher `*` — тобто після **кожного** виклику інструмента. Claude Code передає
hook-у JSON у stdin; `jq` збирає з нього один рядок JSON і дописує його у
`.agent-log/session.jsonl`. Це основа журналювання: без нього ти не відповіси
на питання «що агент насправді робив», спираючись лише на пам'ять.

Формат — **JSONL**, по одному об'єкту на рядок, з полями `ts`, `tool`, `input`,
`result`, `session`, `source`. Він однаковий для всіх інструментів курсу
навмисно: саме це дозволяє покласти поруч журнали двох різних агентів і
порівняти їх, а порівняння двох інструментів — вимога Лабораторної 1. Для
інструментів без зручних hooks той самий формат дає конвертер:

```bash
npm run log:import -- --in <шлях-до-транскрипту> --source auto
```

Два очевидні покращення, які варто зробити самому: розкладати записи по файлах
за сесіями замість одного спільного, і проставляти `result` за фактом, а не
константою `"ok"` — зараз заблокована дія запишеться так само, як успішна.

### Hook 2 — `PreToolUse`, заборона на секрети

```
jq -e '(.tool_input.file_path // "") | endswith(".env") or endswith(".env.local")' >/dev/null && jq -n '{...deny...}' || exit 0
```

Matcher `Write|Edit|MultiEdit`. Якщо шлях, який агент збирається редагувати,
закінчується на `.env` або `.env.local`, hook друкує в stdout рішення про
заборону, і дія не відбувається.

**Контракт блокування** — два рівноправні способи:

1. **Код виходу `2`.** stderr повертається моделі як пояснення, чому відмовлено.
2. **JSON у stdout:**

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "чому саме заборонено"
  }
}
```

Другий спосіб багатослівніший, зате дає моделі осмислену причину і не змішує
відмову з випадковою помилкою скрипта. У прикладі використано саме його.

### Дірки, які залишені навмисно

Приклад ловить `Write`, `Edit` і `MultiEdit` — і **не ловить** `Bash`. Агент,
який виконає `echo ... >> .env`, пройде повз заборону.

Це не недогляд, а частина завдання: у своєму `settings.json` закрий цю дірку і
подумай, які ще шляхи варто захистити (ключі, міграції, `.git/`).

І зверни увагу на зворотний бік: `.agent-log/` навмисно **не** в `.gitignore`, а
твій `.claude/settings.json` — частина здачі. І журнал, і налаштування поїдуть у
git разом із кодом.

Звідси третє покращення, найважливіше: приклад пише в журнал `input:.tool_input`
**цілком**, а для `Write` це весь вміст файлу. Один необережний запит — і секрет
опиняється в закомміченому журналі. Виріши це у своєму `settings.json`: логуй
`file_path` замість повного `tool_input`, або ріж довгі значення, або відфільтруй
чутливі поля. Якщо секрет уже потрапив у журнал — перевипусти ключ і опиши
інцидент, а не видаляй рядок мовчки.
