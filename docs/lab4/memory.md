# Памʼять харнеса і глибоке дослідження

Харнес — мультиагентна функціональність кроку 03 (`scripts/multi/ask.ts`, питання про форк path-to-regexp). Памʼять вмикається прапорцем `--memory`.

## Що памʼять зберігає, а чого не зберігає ніколи
- **decision** — рішення з причиною: «твердження про код — доказом `path#L`, `commit:` — лише для історії»; «підсумок гілки — окремим запитом без інструментів».
- **constraint** — обмеження середовища чи проєкту: «TypeScript 7.0.2 у форку без компіляторного API»; «на master форка `match()` кидає неперехоплений `URIError`».
- **outcome** — результат задачі: «крок 03: −59 % часу читання при тій самій якості»; посилання на прогін — у полі `source`, не в тексті.
- **НІКОЛИ:** секрети, ключі, токени, вміст `.env`; цілі файли й великі фрагменти чужого коду (ліцензія й обсяг); персональні дані.
- **Чим це забезпечено:** детерміновані відмови в [`src/memory/store.ts`](../../src/memory/store.ts) — `reject()`: більше 2 переводів рядка → «схоже на цілий файл»; фрагмент із синтаксисом коду довший за 160 символів → «схоже на фрагмент коду»; непробільний літерал ≥ 32 символів → «схоже на ключ або токен»; слова `api_key|token|secret|password` поруч із `=`/`:` і довгим значенням → «секрет»; `.env` зі значенням → «вміст .env»; email → «персональні дані». Перевіряється лише `text`. Кожна відмова — рядок у `docs/lab4/memory/rejected.jsonl`. Тести: `tests/memory/store.test.ts`.

## Формат store
Файл: [`docs/lab4/memory/store.jsonl`](memory/store.jsonl), один рядок JSON — один запис, схема `entry` (zod, `.strict()`).
| Поле | Тип | Для чого |
|---|---|---|
| at | ISO-час | порядок, найновіші першими |
| kind | decision \| constraint \| outcome | три види, більше не буває |
| text | рядок, ≤ 400 символів | саме твердження (посилань і хешів тут немає) |
| sha | коміт (7–40 hex) | на момент якого твердження було правдою (HEAD названого репозиторію при записі) |
| repo | course \| fork | у якому репозиторії живуть paths — git перевіряє саме там |
| paths | масив шляхів, ≤ 8 | чого твердження стосується (ключ до застарілості); `[]` — глобальне |
| source | рядок, ≤ 300 | звідки взято: вимір, прогін, розділ звіту |

**Хто дописує: ЛИШЕ код** — `remember()` (схема → `reject()` → `appendFileSync`). Модель пропонує запис полем `memory` у чернетці звідника (схема `MemoryProposal`: без `at` і `sha` — їх ставить код). Чому так: Young (Anthropic, 26.11.2025) — перелік тримали в JSON, «because the model is less likely to overwrite it».
**Пропозиції моделі НЕ потрапляють у робочу памʼять автоматично** (OWASP LLM01: прочитане в чужому репозиторії не має ставати моєю постійною інструкцією): після схеми й відмов вони йдуть у `docs/lab4/memory/proposed.jsonl`, а в `store.jsonl` — лише після мого перегляду через `scripts/memory/add.ts --from-proposed N`. Початкові 8 записів — `scripts/memory/seed.ts`, кожен складено з уже перевірених фактів кроків 00–03 і переглянуто мною перед запуском.

## Застарілість — головний режим відмови
- Як виявляється: `git log --format=%H <sha>..HEAD -- <path>` з `cwd` = репозиторій із поля `repo` (`course` — курсовий, `fork` — `LAB4_FORK_DIR`); непорожній вивід = застаріло; помилка git або невідомий коміт = застаріло (падаємо закрито).
- Що робимо: застарілі **не вантажимо в промпт узагалі** (не «позначаємо»): застарілий запис впевнено бреше, а позначку «можливо застаріле» модель легко пропускає; файл при цьому не змінюється, число застарілих іде в трасу (`memory.stale_dropped`).
- Скільком записам це сталося: **2 з 8** — обидва навмисно записані зі старим `sha`, щоб показати механізм:
  - `fork@c439054`, `src/characterization.spec.ts`: «У форку немає жодного тесту на бите %-кодування в match()» — правда на нульовій точці, брехня після `16f2a46` (характеризаційні тести кроку 01);
  - `course@1a7ff70`, `src/multi/fanout.ts`: «Підсумок гілки читання береться з тексту останнього кроку generateText» — правда на `1a7ff70`, брехня після `764b6a8` (окремий запит-підсумок). Саме цей запис, якби потрапив у промпт, відтворював би баг порожніх гілок кроку 03.
- Перевірка в правильному репозиторії й «закрито» — тест `tests/memory/store.test.ts` (sha курсового репо, перевірений у форку, = застаріле; давно не змінюваний файл — свіже).

### Відповідь (із цитатами)
Обмеження в 256 комбінацій було додано до функції pathToRegexp(), щоб запобігти комбінаторному вибуху при обробці шляхів із необовʼязковими групами. Кожна необовʼязкова група подвоює кількість можливих варіантів маршруту, тому наявність кількох таких сегментів поспіль експоненційно множить кількість альтернатив.

У реалізації бібліотеки всі можливі комбінації токенів розгортаються й об'єднуються в один регулярний вираз через оператор чергування. Без жорсткого обмеження це породжує надмірно великий регулярний вираз, що спричиняє перевитрату пам'яті та значне навантаження на процесор під час його компіляції. Межа у 256 комбінацій захищає від подібного вичерпання ресурсів і негайно перериває генерацію викликом відповідного винятку.

Ця поведінка безпосередньо повʼязана з контролем ReDoS у тестовому наборі проєкту, де згенеровані вирази перевіряються бібліотекою recheck. Верифікація вимагає безпечного статусу регулярних виразів і захисту від катастрофічного бектрекінгу. Відсікання шляхів із комбінаторним вибухом запобігає зависанню рушія регулярних виразів та інструментів аналізу безпеки під час обробки надскладних розгалужень.

**Що з цього підтверджено цитатами, а що ні.** Підтверджено (таблиця нижче): межа — це перевірка `combinations >= 256` з `PathError("Too many path combinations")` (`src/index.ts` L460–461); її приніс коміт `22a9679` «Reject large optional route combinations (#424)», який одночасно змінив `src/index.ts`, `src/index.spec.ts` і `src/redos.spec.ts`; тест L216 будує 10 необовʼязкових груп `{/x}` (2¹⁰ = 1 024 варіанти > 256) і чекає саме цієї помилки; ReDoS-тест L14–15 перевіряє кожен згенерований вираз бібліотекою `recheck` на статус `safe`. **Не підтверджено цитатою** — частина другого абзацу (перевитрата памʼяті й процесора під час компіляції виразу): це інтерпретація звідника. **Відповіді не знайдено:** чому саме 256 — ні в коміті (тіло порожнє), ні в Readme/History.md пояснення немає; питання №1 з `context.md` §7 лишається відкритим наполовину.
