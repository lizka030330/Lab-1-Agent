# Крок 02 — верифікатор як остання брама

**Пара:** агент — Gemini 3.6 Flash (OpenCode 1.18.34, `google/gemini-3.6-flash`) → верифікатор — Qwen3 8B локально в Ollama (`ollama/qwen3-8b-16k`, контекст 16k). Брама **локальна**: у GitHub Actions Ollama немає, тому `npm run verify:harness` запускаю перед злиттям гілки агента, після зелених брам кроку 01.

## Чому інша родина

Спершу в `factory.md` я записала верифікатором `gemini-3.5-flash-lite` з Лаб. 2 — «інша модель». Але це та сама родина Gemini, що й агент: спільні дані навчання — спільні сліпі плями, суддя схвалює те, що агент вважає правильним. Тому — Qwen (Alibaba), інша родина і інший постачальник. Плата: суддя слабший (8B) і повільніший (≈ 70–210 с на прогін), зате $0 і без квоти.

## Як влаштовано (`scripts/harness/verify-run.ts`)

| Вимога | Як зроблено |
|---|---|
| Суди лише за доказами | у запит іде дослівна задача, `patch.diff` агента (через `filterDiff`, перевірка на ключі `findSecret`) і коди виходу команд приймання; слова агента не передаються |
| Один суддя — один критерій | окремий запит на кожен критерій з `docs/lab3/criteria.jsonl` (2–4 на задачу) |
| Строга схема | `{id, verdict: pass|fail|unknown, reason, evidence}` (zod); `id` має збігатися з критерієм, для pass/fail `evidence` обовʼязковий |
| Невалідна відповідь | перепитує **рівно раз** із конкретною причиною, потім — помилка і ненульовий код |
| Що блокує | **усе, що не pass** (`isBlocked`): fail і unknown. У Лаб. 2 блокував лише fail (`isBlockedFailOnly` лишився для `scripts/verify.ts`) |
| Економія | якщо брами кроку 01 не зелені (`acceptance_passed` + усі `gates` pass), суддю не запускаю |
| Сліди | вердикт кожного прогону — `docs/lab3/verdicts/<прогін>.json` (модель, час, мс, усі вердикти) |

Строга схема спрацювала в першому ж запуску: Qwen повернула `"id": "t-01"` (номер задачі) замість `"C1"`, двічі поспіль — скрипт зупинився з помилкою, а не прийняв вердикт. Виправлення — у запиті явно сказано, що `id` рівно `C1`, і повторний запит називає причину; схему не послаблювала.

**Єдина розбіжність — хибний pass** (випадок 3, `t-01-1794565498582`, C3 «тести імпортують median»). Агент дописав три тести з `median(...)`, але в `import { docsAtK, mean, … }` median не додав. Суддя написав «тести… які імпортують median» — у diff цього немає. Хибний pass — найнебезпечніша помилка останньої брами: суддя схильний до поблажливості. Свою мітку не змінювала (переписати її під модель — фальсифікація). У цьому прогоні брама все одно спрацювала б: суддя дав fail за C4 (агент переписав `mean`), а `acceptance` не пройшов, тож суддю в режимі брами не запустили б узагалі.
