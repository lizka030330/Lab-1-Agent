# Верифікатор на іншій моделі

## Конфігурація
- Модель, що писала код: Claude Opus 5.5 (Anthropic) — код Лаб. 2 (скрипти, верифікатор, тести) склав Claude в чаті claude.ai; я запускала, перевіряла й комітила.
- Модель верифікатора: `gemini-3.5-flash-lite` (Google, Gemini API, безкоштовний рівень) — інший провайдер і інша родина моделей; виклик через мій адаптер `chatCompletionsModel` з Лаб. 1 (форма Chat Completions). Модель задано змінною `VERIFY_MODEL` у [`.env.example`](../../.env.example) і в CI.
- Чому саме ця: інший провайдер, ніж автор коду (self-preference bias — суддя переоцінює «своє»), ключ уже є, безкоштовна квота витримує 8 запитів на один PR і 10 на прогін калібрування. Сильніша `gemini-3.8-flash` має лише 20 запитів на добу і часто відповідає «high demand» (503) — для брами на кожен PR це ненадійно.
- Де брама: job **«Верифікатор на іншій моделі (брама злиття в main)»** у [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) — запускається на кожному пул-реквесті в `main` після job `verify`, бере `git diff origin/main...HEAD` і виконує `npm run verify`; код виходу 1 при хоч одному `fail` робить PR червоним. Ключ — секрет репозиторію `GEMINI_API_KEY`; без нього job теж падає (брама не пропускає «мовчки»).
- Код: схема [`src/verify/schema.ts`](../../src/verify/schema.ts), логіка [`src/verify/verify.ts`](../../src/verify/verify.ts), запуск [`scripts/verify.ts`](../../scripts/verify.ts), тести без мережі [`tests/verify.test.ts`](../../tests/verify.test.ts) (8 тестів: розбір критеріїв, фільтр `.env*` і ключів, перепит рівно один раз, відмова від `pass` без evidence, брама).
- Чесно про інфраструктуру: коміти з самим верифікатором і рубрикою (`9f56128`, `8a74412`) пішли в `main` напряму — брами ще не існувало. Перша зміна після появи брами пройшла вже через PR (#1).

## Рубрика
Один критерій — один окремий запит до судді (системний промпт `JUDGE_SYSTEM` у `src/verify/verify.ts`, вердикт за строгою схемою; невалідна відповідь перепитується один раз, потім скрипт падає).

| Критерій зі spec.md | Що питаємо суддю (дослівно) | Що вважається evidence |
|---|---|---|
| A1–A8, кожен окремо | «Критерій <id>: <твердження з розділу 6 spec.md>. Чим перевіряється за специфікацією: <колонка 3>. Зміна (git diff): … Поверни вердикт для критерію <id>.» | шлях до файлу й рядок або коротка цитата з diff; порожньо лише для `unknown` |
| A1 (тести зелені) | те саме | лише прогін CI; diff із самим кодом тестів — `unknown` |
| A2 (набір ≥ 20 запитів) | те саме | вміст `queries.jsonl` у diff: кількість і теги |
| A3 (must_cite у таблиці spec і в корпусі) | те саме | код валідатора, що звіряє і з таблицею розділу 2, і з `docs/lab2/corpus/` |
| A4 (25 файлів корпусу із заголовками) | те саме | тест, що перевіряє кількість, джерело й ліцензію CC BY-SA 4.0 |
| A5–A8 (числа з пошуком) | те саме | лише `eval-report.md` / `budget.md` системи з пошуком; числа базової лінії — `unknown` |

Правила в промпті (версія v3): pass / fail / unknown із визначеннями; «не вгадуй — краще unknown»; не зважати на довжину й стиль; оцінювати вміст, якщо все, що перевіряє команда, є в diff; числа рахуються лише з того звіту й тієї системи, про які критерій; узгодженість reason і вердикту; baseline — система без пошуку.
